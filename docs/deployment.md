# Deployment, backup & recovery

## Production checklist

- [ ] PostgreSQL 14+ with automated backups
- [ ] HTTPS terminated in front of SmartNest (required: session cookies are `Secure` in production)
- [ ] `NODE_ENV=production`
- [ ] `CREDENTIAL_ENCRYPTION_KEY` — 32 random bytes, base64 or hex (`node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"`)
- [ ] `STREAM_TOKEN_SECRET` — 32 random bytes, base64 or hex
- [ ] `WEB_ORIGIN` and `PUBLIC_APP_URL` set to the public HTTPS origin
- [ ] `ALLOW_PRIVATE_INTEGRATION_HOSTS=false` if SmartNest is hosted outside the home network and users must not reach private ranges
- [ ] Secrets stored in your platform's secret manager, not in images or git
- [ ] Exactly **one** SmartNest server instance per database (stateful integration connections + in-process scheduler)

## Hosting from GitHub

GitHub Pages only serves static files, so it cannot run SmartNest (an API server, PostgreSQL and long-lived WebSocket connections). The repository is instead wired up so that GitHub runs the pipeline and Render hosts the app, deploying from the repo.

### Pipeline (`.github/workflows`)

| Workflow | Trigger | What it does |
| --- | --- | --- |
| `ci.yml` | every pull request (and called by `release.yml`) | `lint:secrets`, strict typecheck, shared/server/web tests against a PostgreSQL service, production build, Playwright E2E with the mock Home Assistant (report uploaded on failure), Docker build check |
| `release.yml` | push to `master`/`main`, or run manually | runs the whole CI suite, then publishes the image to `ghcr.io/<owner>/<repo>` tagged `latest` and `sha-<commit>` |
| `dependabot.yml` | weekly/monthly | dependency, GitHub Actions and base-image update PRs (each one goes through CI) |

No repository secrets are required: the image is pushed with the built-in `GITHUB_TOKEN`. The published package is private by default; change it under the repo's **Packages → Package settings** if you want to pull it without logging in.

Recommended: **Settings → Branches → add a rule for `master`** requiring the `CI` checks to pass before merging, so nothing untested reaches the deploy branch.

### Deploy on Render (`render.yaml`)

1. Push the repository to GitHub (including `render.yaml`).
2. In Render: **New → Blueprint**, connect GitHub, and select the repository. Render creates:
   - `smartnest` — a Docker web service built from the root `Dockerfile`, health-checked on `/api/health`;
   - `smartnest-db` — PostgreSQL 16, wired in as `DATABASE_URL`.
3. `CREDENTIAL_ENCRYPTION_KEY` and `STREAM_TOKEN_SECRET` are generated by Render on first creation and kept across deploys. **Copy `CREDENTIAL_ENCRYPTION_KEY` somewhere safe** (see Backups).
4. Open `https://smartnest.onrender.com` (or the URL Render shows). `WEB_ORIGIN`/`PUBLIC_APP_URL` default to that URL; set both explicitly if you add a custom domain.

After that, every push to `master` deploys automatically once its GitHub checks have passed (`autoDeployTrigger: checksPass`). Migrations run on container start.

Notes for this hosted setup:

- `ALLOW_PRIVATE_INTEGRATION_HOSTS=false`: a cloud server can't (and must not) reach your home LAN. Connect Home Assistant through a public HTTPS URL such as Home Assistant Cloud (Nabu Casa) or your own reverse proxy, or use demo mode.
- The blueprint uses **free plans** so you can try it at no cost. A free web service sleeps after about 15 minutes idle (automations, schedules and live integration connections pause until the next request) and a free database expires after 30 days. Switch to `plan: starter` and a paid database plan for real use.
- Keep `numInstances: 1` — see the checklist above.

### Other hosts

Any container platform works with the published image (`ghcr.io/<owner>/<repo>:latest`): Fly.io, Railway, Azure Container Apps, Google Cloud Run (set min instances = max instances = 1), or your own server with `docker run` as below. Provide `DATABASE_URL`, both secrets, `WEB_ORIGIN` and `PUBLIC_APP_URL`, and terminate HTTPS in front of it.

## Docker

The root `Dockerfile` builds a single image serving the API and the built web app on one port (8080), running `prisma migrate deploy` on start, as a non-root user, with a health check on `/api/health`.

```bash
docker build -t smartnest .
docker run -d --name smartnest -p 8080:8080 \
  -e DATABASE_URL='postgresql://user:pass@db-host:5432/smartnest' \
  -e CREDENTIAL_ENCRYPTION_KEY='…' -e STREAM_TOKEN_SECRET='…' \
  -e WEB_ORIGIN='https://home.example.com' -e PUBLIC_APP_URL='https://home.example.com' \
  smartnest
```

Or locally with Compose: put the two secrets in `.env`, then `docker compose --profile app up -d --build` (http://localhost:8080).

## Without Docker

```bash
npm ci
npm run build
npm run db:deploy -w @smartnest/server      # prisma migrate deploy
NODE_ENV=production node apps/server/dist/index.js   # serves apps/web/dist when present (STATIC_DIR to override)
```

## Reverse proxy (TLS + WebSocket)

Caddy:

```
home.example.com {
  reverse_proxy 127.0.0.1:8080
}
```

nginx:

```nginx
location / {
  proxy_pass http://127.0.0.1:8080;
  proxy_http_version 1.1;
  proxy_set_header Upgrade $http_upgrade;     # /api/ws
  proxy_set_header Connection "upgrade";
  proxy_set_header Host $host;
  proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
  proxy_set_header X-Forwarded-Proto $scheme;
  proxy_buffering off;                        # camera MJPEG streams
  proxy_read_timeout 1h;
}
```

The server trusts one proxy hop in production (`trust proxy = 1`) for client IPs and rate limiting.

## Upgrades

1. Back up the database.
2. Deploy the new image/build — migrations run automatically (`prisma migrate deploy`) and are forward-only.
3. Check `/api/health` and the Integrations page (all integrations should return to "Connected").

## Backups

What to back up: the PostgreSQL database **and** `CREDENTIAL_ENCRYPTION_KEY`. Without the key, stored integration tokens cannot be decrypted (users would need to reconnect integrations; nothing else is lost).

```bash
pg_dump --format=custom --no-owner "$DATABASE_URL" > smartnest-$(date +%F).dump
```

Schedule daily dumps with retention (e.g. 14 daily, 8 weekly), store them encrypted off-host, and test restores regularly.

## Recovery

```bash
createdb smartnest_restore
pg_restore --no-owner --dbname "postgresql://…/smartnest_restore" smartnest-YYYY-MM-DD.dump
# point DATABASE_URL at the restored database and start SmartNest with the same CREDENTIAL_ENCRYPTION_KEY
```

After a restore, commands that were in flight are marked "timed out" automatically, adapters reconnect and re-read device state from the integrations (device state is never trusted from the backup alone).

## Key rotation

- `STREAM_TOKEN_SECRET`: rotate any time; only active camera views (≤ 60 s tokens) are affected.
- `CREDENTIAL_ENCRYPTION_KEY`: rotating makes stored tokens unreadable — affected integrations show "auth failed"; reconnect each with a new token. (Re-encryption tooling is not included in this version.)

## Monitoring

- `GET /api/health` → `200 {status:"ok", db:"ok"}` or `503`.
- Structured JSON logs (pino) on stdout; set `LOG_LEVEL`.
- Watch for `integration.error` activity entries and the Integrations page status.
